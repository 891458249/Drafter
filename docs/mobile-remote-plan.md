# DeskTopUI 移动端远程控制 · 策划案

> 版本:v0.1(2026-08-10) 状态:待评审
> 目标:让 DeskTopUI 走出桌面——手机端随时随地给电脑端下达任务,电脑端基于本地项目自动执行,结果回流手机。

---

## 一、背景与机会

DeskTopUI 目前是 Windows 桌面端(Electron + Claude Agent SDK),已具备:

- 完整的会话引擎(`src/main/sessions.js`):创建/resume/分支/编辑重生成/定时任务(scheduler)
- 六板块渲染端、Gem 自定义助手、AIGC 生成、消息导航等成熟 UI
- 稳定的 IPC 契约:`sess:create/send/history/interrupt/editRegenerate/branch`、`aigc:send`、`gems:*` 等 60+ 通道
- GitHub Release + electron-updater 自动更新链路

**核心洞察:手机端不需要重做任何 AI 能力,它只是"第二个渲染端"。**
所有会话逻辑、SDK 调用、项目上下文都在电脑主进程里,手机端只需要一个「通道 + 轻 UI」。

用户场景:

| 场景 | 描述 |
|---|---|
| 通勤路上派活 | 出门在外想到一个需求,手机上下达"把 XX 项目的登录页改成深色主题",到家时电脑已完成 |
| 长任务监控 | 电脑上跑着耗时重构,人在外面用手机看流式进度,必要时打断或追加指令 |
| 远程审批 | 任务执行到需要确认的工具调用(写文件/跑命令),手机弹审批,点"允许"继续 |
| 结果验收 | 任务完成推送通知,手机上查看 diff 摘要,满意就让它 commit,不满意就打回重做 |

## 二、总体架构

### 2.1 架构选型对比

手机与电脑之间的通道有三个候选方案:

| 方案 | 原理 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **A. 局域网直连** | 电脑端起 HTTP/WebSocket 服务,手机同 WiFi 直连 | 零服务器成本、延迟低、数据不出内网 | 离开家/公司 WiFi 就失联;手机要输 IP | **MVP 采用** |
| **B. 云端中继** | 自建/租用 broker,双端 WebSocket 长连,消息经服务器转发 | 任意网络可达、无需穿透 | 服务器成本、消息过云的隐私顾虑、开发量大 | **二期** |
| **C. 内网穿透/Tailscale** | 借助 Tailscale/ZeroTier 组虚拟内网,再直连 | 任意网络可达、端到端加密、无自建服务器 | 依赖第三方服务、用户需装额外 App | **二期可选,给进阶用户** |

**推荐路线:一期 A(局域网直连)打通全链路 → 二期加 B/C 解决"人不在同一网络"的核心场景。**

理由:远程派活的 *交互协议、配对安全、手机 UI、电脑端服务化改造* 与通道方案完全解耦。先用局域网把这套东西做实,二期只换传输层。

### 2.2 目标架构图

```
┌─────────────┐         ┌──────────────────────────────────┐
│   手机端     │  WSS    │  电脑端 DeskTopUI                  │
│ (浏览器/PWA) │◄───────►│  ┌────────────────────────────┐  │
│  或套壳 App  │  JSON-RPC│  │ remote-server.js (新增)     │  │
└─────────────┘         │  │  - WebSocket 服务 + TLS      │  │
                        │  │  - 配对/token 鉴权           │  │
                        │  │  - 协议适配层                 │  │
                        │  └──────────┬─────────────────┘  │
                        │             ▼                    │
                        │  ┌────────────────────────────┐  │
                        │  │ sessions.js (现有,不改核心) │  │
                        │  │ store / gems / aigc / git   │  │
                        │  └────────────────────────────┘  │
                        │             ▼                    │
                        │     Claude Agent SDK → 本地项目    │
                        └──────────────────────────────────┘
```

关键设计:**remote-server 只做"IPC 协议的 WebSocket 翻译"**,把现有 `sess:*` 等 IPC 通道语义原样暴露为 JSON-RPC 消息,渲染端那套事件流(`text delta` / `usage-updated` / `turn-done` / 权限请求)也原样转发。这样:
- 电脑端渲染进程逻辑零改动;
- 手机端拿到的事件流与桌面端完全一致,UI 只是缩小版;
- 未来桌面端加新功能,远程端几乎自动获得。

## 三、协议设计(JSON-RPC over WebSocket)

### 3.1 消息类型

```jsonc
// 请求(手机 → 电脑)
{ "id": 1, "method": "sess.create", "params": { "projectId": "...", "prompt": "把登录页改深色主题", "gem": "前端助手" } }
// 响应
{ "id": 1, "result": { "sessionId": "..." } }
// 事件(电脑 → 手机,推送)
{ "event": "sess.delta",    "params": { "sessionId": "...", "text": "..." } }
{ "event": "sess.turnDone", "params": { "sessionId": "...", "usage": {...}, "durationMs": 12345 } }
{ "event": "perm.request",  "params": { "sessionId": "...", "tool": "Bash", "detail": "npm run build" } }
```

### 3.2 一期协议范围(对表现有 IPC)

| 远程方法 | 对应现有 IPC | 说明 |
|---|---|---|
| `pair.request` / `pair.confirm` | (新增) | 配对流程,见 §4 |
| `proj.list` | `proj:list` | 项目列表 |
| `sess.list` / `sess.history` | `sess:list` / `sess:history` | 会话列表与历史回放 |
| `sess.create` / `sess.send` | `sess:create` / 发消息 | 下达任务(可带 Gem、附件说明) |
| `sess.interrupt` | `sess:interrupt` | 打断 |
| `perm.respond` | perms 模块 | 远程审批(允许/拒绝/始终允许) |
| `git.diffStat` | `git:diffStat` | 结果验收摘要 |
| 事件:`sess.delta` / `sess.turnDone` / `sess.usage` / `perm.request` / `sess.error` | 现有 webContents.send 事件 | 流式推送 |

二期再暴露:`sess:branch`、`sess:editRegenerate`、`aigc:send`、`cron:*`、文件树浏览与图片预览。

## 四、安全设计(重中之重)

远程开放的是**能在你电脑上读写文件、执行命令的 Agent**,安全门槛必须拉满:

1. **配对制,非账号制**(一期):电脑端「设置 → 移动端」生成 6 位配对码 + 二维码(内含局域网地址+一次性码),手机扫码 10 分钟内完成配对,双方保存长期 token(电脑端存 store,手机端存 localStorage)。配对码一次性,token 可随时在电脑端吊销。
2. **TLS 自签证书**:配对时下发证书指纹,手机端 pinning;局域网内防同网段嗅探。
3. **权限分级**:
   - 远程发起的会话**默认更严格的工具审批模式**(每次写文件/执行命令都要手机确认),不因桌面端的宽松设置而放松;
   - 提供「免审批白名单」:仅允许只读类工具自动通过;
   - 「放手模式」为显式开关,开启时明确提示风险,且按会话生效、带超时自动回落。
4. **审计**:远程会话在会话列表打 📱 标记,所有远程操作(含审批记录)进 logger。
5. **网络面收敛**:默认只绑局域网网卡;发现/广播用 mDNS 或手动扫码,不做公网端口映射。二期中继方案中,消息体端到端加密(中继只转发密文)。

## 五、电脑端改造清单(落到模块)

| 改动 | 位置 | 工作量估计 |
|---|---|---|
| 新增 `remote-server.js`:WS 服务、TLS、token 鉴权、协议适配、事件转发 | `src/main/` 新模块 | 3–4 天 |
| 配对管理:生成/校验配对码、二维码渲染、已配对设备列表与吊销 | `src/main/` + 设置页 UI | 1–2 天 |
| 远程权限策略:远程会话强制审批模式 + 白名单 + 放手模式开关 | `perms.js` / `sessions.js` | 1–2 天 |
| 完成通知已有(回合 toast),补充:非活跃远程会话完成时向手机推送 | `sessions.js onTurnDone` | 0.5 天 |
| 防休眠选项:远程会话运行期间阻止系统睡眠(powerSaveBlocker) | `main.js` | 0.5 天 |
| 设置页「移动端」板块:开关、二维码、设备列表、放手模式 | 渲染端设置 UI | 1 天 |

**电脑端总计约 7–9 天。** 复用度极高,无第三方重依赖(ws + 自签证书生成即可,均纯 JS)。

## 六、手机端形态与功能

### 6.1 形态选型

| 形态 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| **PWA(手机浏览器打开)** | 零上架成本、一套代码、复用现有渲染端样式 | iOS 推送受限、体验略逊于原生 | **一期采用** |
| React Native / Expo | 原生体验、推送完善 | 技术栈分叉、要维护两套 UI | 二期视反馈 |
| 微信小程序 | 免安装、触达方便 | 长连接限制(需轮询/wx socket)、审核、代码隔离 | 不推荐 |

**一期:PWA。** 桌面端渲染端本身就是纯 HTML/JS(marked/hljs 都在),把 `chat.js / state.js / styles.css` 抽出一个 mobile 变体,工作量远小于想象。电脑端直接托管这个 PWA(扫码即开),连分发都不需要。

### 6.2 手机端 MVP 功能(P0)

1. 扫码配对 + 设备管理
2. 项目/会话列表(📱 标记远程会话)
3. 下达任务:输入框 + 选项目 + 选 Gem(复用 Gem 体系,手机上也能选"前端助手"这类预设人格)
4. 流式查看:文本流式渲染 + 代码块卡片(直接复用 codeblock.js/hljs.js)
5. **远程审批弹窗**:工具调用确认(允许一次/拒绝),带震动提醒
6. 回合完成通知(PWA 内横幅 + 系统通知 where possible)+ 结果摘要(tokens/用时/diff 统计)
7. 打断按钮

### 6.3 二期功能(P1/P2)

- P1:消息分支/编辑重生成、图片附件拍照上传(手机拍照 → 当附件发给任务,天然场景)、任务完成后的 diff 全文查看
- P1:云端中继通道(任意网络可达)
- P2:AIGC 板块远程使用、定时任务管理、多电脑管理(一台手机控多台)
- P2:语音输入派单(手机端语音转文字直达任务框)

## 七、关键交互流程

### 7.1 配对(一次性,约 30 秒)

```
电脑:设置 → 移动端 → 开启远程服务 → 显示二维码
手机:浏览器扫码 → 打开 PWA → 自动带配对码 → 电脑弹确认("允许「小明的 iPhone」接入?")
→ 双方存 token → 手机进入主界面
```

### 7.2 下达任务(核心路径,目标 < 20 秒)

```
手机:选项目(或沿用上次)→ 输入"把登录页改深色主题"→ (可选 Gem)→ 发送
电脑:remote-server 鉴权 → sess.create → SDK 开始执行 → 事件流转发
手机:流式看到执行过程;遇工具审批弹窗 → 点允许
电脑:回合完成 → 手机收通知「✅ 完成 · 12.4k tokens · 3分12秒 · 改动 5 个文件」
手机:点进看 diff 摘要 → 追加指令"提交并推送" 或 "回滚重做"
```

### 7.3 异常路径

- 电脑离线/断网:手机端显示设备离线,任务可存草稿,上线后手动重发(二期中继可做离线队列自动补发)
- 电脑休眠:远程会话运行期间 powerSaveBlocker 防睡;无任务时允许睡,睡后手机端显示"电脑已休眠"
- 审批超时:默认 5 分钟无响应自动拒绝并通知,防任务卡死

## 九、风险与对策

| 风险 | 等级 | 对策 |
|---|---|---|
| 远程开放执行权限被滥用 | 🔴 高 | §4 全套:配对+TLS+强制审批+审计+可吊销;默认只绑内网 |
| iOS PWA 通知/长连受限 | 🟡 中 | 前台用 WS;后台降级:回合完成时电脑端 toast + 手机下次打开补拉;二期 RN 解决 |
| 电脑休眠/关机导致"派了没人干" | 🟡 中 | 运行期防睡 + 设备在线状态心跳 + 手机端明确提示 |
| 家庭网络 NAT/换 IP | 🟢 低 | 二维码含当前局域网地址,每次打开设置页刷新;或 mDNS 发现 |
| 二期中继的消息隐私 | 🟡 中 | 端到端加密,中继只见密文;密钥派生自配对 |
| 范围膨胀(想做全功能手机端) | 🟡 中 | 严守 P0 清单;二期功能按真实使用反馈排序 |

## 十、成功度量

- 配对成功率 > 90%(30 秒内完成)
- 派单路径 < 20 秒(打开 PWA → 任务发出)
- 远程会话审批平均响应 < 2 分钟
- 周活跃远程会话数、二期通道需求投票(决定 M4 方向)

## 附:为什么是现在

桌面端刚完成 Gem 体系(v0.9.11)和流式性能优化(v0.9.10),会话引擎与事件流已稳定,是把"第二个客户端"接进来的最佳时点——再晚,桌面端独有功能越积越多,协议适配面会更大。建议 v0.9.13 收尾后,v1.0.0 以「移动端远程控制」作为旗舰特性发布。
